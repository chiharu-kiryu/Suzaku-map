## N07：首次状态覆盖启动阶段的新选择

在私有 Xvfb 中创建真实主面板和设置窗口，通过实际命中区执行点击，然后调用应用自己的
设置窗口 → 主窗口事件路径；不直接把“用户选择”赋给主窗口。

1. `PredictionSettingsSync` 尚无已确认状态，默认 Tone 为 Balanced。
2. 用户点击 Focused（2）或 Expressive（7）。两窗口和面板配置文件都已更新。
3. 因为没有首次确认基线，`next_patch` 暂时不会发送补丁。
4. 宿主首次状态到达，仍是 Balanced（4）。

两种点击的实际结果均为：

```text
panel=Balanced, settings=Balanced, saved=Balanced, next_patch=None
```

期望是保留用户刚作出的显式选择，待首次状态建立基线后发出对应补丁，或在初始同步前
明确禁止编辑；不能把已经接受的点击当成旧缓存无声丢掉。

根因：[`PredictionSettingsSync::observe`](../src/bin/panel/prediction_settings.rs)
在 `confirmed=None` 时无条件用宿主值覆盖控件，没有记录首次状态之前的用户修改。
[`PanelApp::apply_native_settings`](../src/bin/panel.rs) 随后把覆盖结果同步到另一个窗口
并保存到面板配置文件。

对照：先收到首次状态，再做同样点击、状态刷新及 ACK，两种 Tone 都会正确保留并仅发送一次。
原有“刷新前有未发送编辑”测试已经先调用过 `observe`，没有覆盖启动时的空基线。
这里人为控制事件次序以复现边界，没有将具体机器上的状态延迟量化成固定时间。

## N08：窄设置补丁覆盖尚未重载的新配置

测试使用真实 `suzaku_tool model configure` 子进程、临时配置文件，以及宿主实际的
[`suzaku_host_ime_control_utf8`](../src/ime_host.rs) 处理函数。
不启动或注册真实 IBus，不激活会话，不输入文本；**所有场景联想始终关闭**。

复现序列：

1. 宿主载入配置 A，随后保持运行状态的内存快照。
2. 命令行成功保存配置 B，尚未选择托盘中的“重新加载模型配置”。
3. 发出与模型身份无关的操作：改温度 `U`、关闭联想 `P0`，或改输入语言 `Lja`。
4. 操作回复成功，但磁盘上的 B 被旧 A 加这次小修改覆盖。

| 命令行已保存的改变 | 后续窄操作 | 实际丢失的设置 |
| --- | --- | --- |
| 新本地模型 `synthetic-new`、超时 1234 ms | U / P0 / Lja | 模型被改回 `auto`，超时回到 1200 ms |
| 云端授权由 `true` 撤销为 `false` | U / P0 / Lja | 文件中的授权被改回 `true` |
| 云端地址及模型改变，授权按设计自动撤销 | U / P0 / Lja | 新目标丢失，旧目标及旧授权 `true` 一同写回 |

这 3 类改变 × 3 个控制操作均复现。合成云端地址位于 `.invalid` 域，未联系任何模型服务；
这是已确认的**配置/授权状态回退**，不是声称已经观察到输入内容外传。

CLI 明确提示保存后需要重载，所以宿主在重载前继续使用内存配置本身不是本问题。
问题是：无关的小设置操作会销毁“已保存、等待重载”的新文件，让之后再重载也找不回 B。

根因：宿主控制函数先 `session.settings.clone()`，再修改一两个字段，最终 `settings.save()`
保存整个旧配置；没有检查磁盘是否已经由另一个受支持的入口修改。
[`ImeSettings::save`](../src/ime/settings.rs) 的原子替换保证单文件完整性，但不检测旧版本覆盖；
[`DataLease`](../src/data/files.rs) 的共享锁用于阻止恢复，不是各配置写入者之间的排他锁。

对照：只查询状态不写坏文件；明确重载 B 后再执行同样操作，9 个场景均保持 B 的其他字段。
在修复前，临时规避方式是保存新配置后先立即重载，不在两者之间操作温度、联想开关或语言。

建议修复边界：检测磁盘与宿主内存的配置冲突，并保留新文件。可以明确拒绝并要求重载，
也可以在串行化/版本检查保护下只合并用户本次修改的字段；不能借此静默切换新模型目标，
尤其不能恢复已撤销的云端授权。诊断接受“正确合并”或“不写坏文件地拒绝冲突”两种结果。

## N09：外观配置保存失败没有可见反馈

1. 私有配置目录中已成功保存朱雀主题。
2. 暂时把这个测试专用目录设为只读（0500），先确认保存函数确实返回错误。
3. 通过设置窗口实际点击白虎，并经过两窗口同步事件。
4. 两窗口均显示白虎，原设置文件逐字节保持不变，两窗口的错误反馈均为空。
5. 使用同一临时配置新建面板，加载出的仍然是朱雀。

这是“界面已改但没有保存成功”的反馈问题，不是原子写入损坏了旧文件。
根因是 [`PanelState::persist_display_settings`](../src/bin/panel/controller.rs)
使用 `let _ = save_display_settings(...)`，丢弃了底层错误；相关调用已先修改内存控件，
没有回退或标记“未保存”。

对照：旧文件在失败时保持完整；恢复测试目录权限后，再明确选择青龙可正常保存。
目录权限由局部守卫恢复，所有文件仅存在于本次临时目录，没有修改用户配置权限。

建议修复边界：让两窗口显示可理解的保存失败/未保存状态，或回退本次偏好；不要在事件
循环中无限重试。成功反馈必须以实际保存成功为准，恢复可写后由明确操作或受控重试保存。

## 已实施的修复

### N07：区分显式点击与启动缓存

联想开关、温度分别记录运行期编辑代次，设置窗口将其同步给主窗口，不写入偏好文件。
首次状态只覆盖没有被用户显式编辑的控件，再为保留的新选择生成待确认补丁。
加载旧偏好不算点击，因此不会因上次保存的 `On` 自动重新启用联想。

在途补丁同时记录发送时的编辑代次；迟到的失败只回退之后未被重新编辑的控件，
避免“选 A → 选 B → 再选 A”被当成没有新操作。成功确认和失败停止重试的原语义保留。
额外单元测试覆盖首次选择与初始值相同的 Off / Balanced、旧偏好，以及同值重选的迟到失败。

### N08：拒绝冲突，保留待重载文件

[`ImeSettings::save_if_unchanged`](../src/ime/settings.rs) 在写入前比较预期配置与磁盘配置。
宿主温度、联想、语言操作使用宿主内存配置作为基线；不匹配时明确拒绝，提示先重新加载，
不改变磁盘新配置或宿主当前配置。面板发起操作的失败也会显示在主面板，而非仅留在托盘状态。

[`DataLease::settings_writer`](../src/data/files.rs) 提供单独的非阻塞排他写锁，覆盖比较到
原子替换的区间；它与生命周期/恢复共享锁分离，不升级运行中的锁，也不等待其他写入者。
普通设置保存使用同一写锁；[`model configure`](../src/bin/suzaku_tool/model.rs) 同样使用
读取基线进行条件保存，防止 CLI 自身覆盖读取之后发生的新修改。

这是 Suzaku 配置写入者之间的串行化保护，不声称能锁住不遵守该约定的任意外部编辑器。
明确重载仍是采用新配置的必要步骤；保存撤销授权不会被无关小修改重新写回，但此修复
**不等于把磁盘上的撤销即时应用到尚未重载的宿主内存**，也不会静默切换模型目标。

回归除原有 3 × 3 冲突矩阵外，还验证：持锁时控制操作快速失败且保留原文件；CLI
写锁竞争；旧读取者条件保存被拒绝；无效外部 JSON 不被小操作销毁；明确重载后可继续修改。

### N09：保留预览，明确标记未保存并允许重试

主面板不再丢弃保存错误：失败后保留当前预览、旧文件保持完整，同时发出错误反馈。
设置标题持续显示“未保存”和“重试”，关闭再打开设置仍可发现未保存状态；提示与按钮
提供八语文案，窄窗口/大字号下保持完整可读，不改变设置正文的高度或位置。

只有实际保存成功才清除失败状态；恢复权限后的普通重绘不会反复写文件。用户点“重试”
会通过设置窗口 → 主窗口持久化通道保存当前预览，成功后两窗口同步清除警告；之后正常
更改主题仍可保存。隔离测试实际点击按钮并检查落盘、旧文件字节和两窗口状态。
