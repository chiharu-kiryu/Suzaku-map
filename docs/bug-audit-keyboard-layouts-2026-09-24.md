# 物理键盘与布局审计 · 第三十二轮（2026-09-24）

沿 [功能网络](functional-network.md) 的 F08–F13，补测此前主要依赖已解析 keyval 的
修饰键路径：真实应用收到物理键码后，布局、锁定状态和组合键能否正确进入连续草稿。
基线是 `0.6.5` / `088c5d94e49b701e9c11074c650ea558a9a59a55`。

本轮 **未确认新的产品缺陷**，不新增 N 编号，不修改输入规则。新增测试、CI 配置

## 入口与隔离

```bash
bash scripts/test-linux-apps.sh keyboard
```

[运行器](../scripts/test-linux-apps.sh) 新增 `keyboard` 入口，依赖既有 GTK/XTest
环境以及 `setxkbmap`、`xkbcomp`（Ubuntu 的 `x11-xkb-utils` 包）。所有测试都在新建
的 Xvfb、D-Bus/IBus、运行目录与合成文档中进行，不连接个人 X11/Wayland 会话。
[专项脚本](../scripts/test-linux-keyboard.py) 先加载已有隔离断言，再允许任何 XKB 改动。

在初始美式布局下记录物理键码。之后保持这些键位，用 XTest 发送真实的按下/释放，
让 **XKB → GNOME Text Editor/GTK → IBus → Suzaku** 解析字符，而不是直接向引擎
传入想要的 Unicode/keyval。每次组合键都在 `finally` 释放；检查没有残留按住的修饰键。
布局和锁定的切换仅是测试动作，不是 Suzaku 的启动或输入操作。

除空草稿数字直通组外，提交前通过真实 Ctrl+S 保存确认正文仍为空，草稿未被快捷键
结束；Enter/小键盘 Enter 后检查准确正文、没有重复提交和候选装饰。读取 XKB 状态、
具名 Caps/Num 指示器及整份键盘映射，确认引擎没有改变锁定/灯的服务器状态或键位。
这验证的是 **Xvfb 的 XKB 指示状态，不是实体键盘硬件灯**。

## 26 组覆盖

- **6 组大小写：** Caps 关/开分别组合不按 Shift、左 Shift、右 Shift，实际输出
  `abc`/`ABC`，同时校验锁定与对应指示状态；大小写不会反向或被再次转换。
- **4 组补全：** Caps/Num 的四种组合下，`hel`/`HEL` 数字采用、立即退格撤销、
  再采用和空格续写，最终分别准确提交 `hello ` / `HELLO `。
- **2 组小键盘：** NumLock 开启时，草稿中的十个数字、小数点及四种运算符均按
  字面加入；空草稿 `12.5` 则直接进入应用，不启动候选。小键盘 Enter 只提交一次。
- **5 组布局：** 美式、英式、德式、法式、美式国际配置。覆盖 Shift 标点、英镑、
  德式 Y/Z、AltGr 的 `@`/`€`/花括号、法式字母/重音/Shift 数字，以及死键产生的
  `café ü`。所有断言都基于真实键位，不以期望字符代替键盘事件。
- **3 组组合操作：** 左右 Shift 分别测试反向 Tab、小键盘采用/撤销和 Ctrl 删词；
  另验证 Alt 数字与物理 Compose 的 `½` 不误选候选、不提前上屏。
- **6 组输入中途变化：** 草稿中切 Caps、切 NumLock、美/德/法布局连切；重音组合
  分别由 Esc/Backspace 仅取消未完成重音；私有 Compose 表的多词结果仍在可编辑草稿中。

模型联想关闭，不启动实际模型，不使用个人 Compose 文件。自定义 Compose 只用
仓库已有私有夹具，其中多词结果不能被误当成数字选择或应用快捷键。
