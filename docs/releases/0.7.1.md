# Suzaku 0.7.1 · Linux Alpha activation diagnostics and installation audit

For **Ubuntu 24.04 amd64, IBus, X11 / GNOME XWayland**. This is a maintenance
release, still an Alpha; keep a fallback input method. Production input behavior,
Chinese/English vocabulary, Japanese compatibility, shortcuts and model boundaries
are unchanged. Other platforms are not newly release-qualified.

## Highlights

- **Actionable activation failures:** private native IBus tests now retain the real
  CLI's command arguments, stderr and exit codes when activation, restoration or the
  final engine check fails. Timeout reports use the same bounded 16 KiB diagnostic tail.
  The wrapper preserves stdout and failure status; it does not mask failed tests.
- **Strict fixture boundaries:** diagnostics require the private runtime and IBus address,
  the explicit test marker and no desktop display. Self-recursion, missing executables
  and unrelated commands are rejected. No drafts or personal typing are recorded.
- **Explicit repeat checks:** the activation-only mode runs 10 cycles by default,
  configurable from 1 to 20. It stops at the first failure. Ordinary full-suite CI
  behavior and production release/restore logic are unchanged; there is no blanket retry.
- **Resource-safe local validation:** contributor and repository instructions describe
  serial, single-job checks in a task-owned memory-limited systemd scope. Limits apply
  only to the check and its children; no desktop-wide memory or process settings change.
- **Installation evidence retained:** the packaged audit records 124 isolated checks
  against installed 0.7.0 binaries, 13 completed real GNOME input cases, and actual
  tray/service quit and reopen. Two remaining desktop cases were stopped by the focus
  guard and are not claimed as passed. Personal settings and the previous input source
  were restored. These are historical 0.7.0 results, not a new 0.7.1 installation test.

## Original CI failure remains unconfirmed

The first 0.7.0 CI attempt failed in native input-source restoration. The unchanged
implementation passed 130 repeated local/container cycles, including constrained-CPU
and fresh private-bus cases. Rerunning only the failed Linux job at the same commit
completed successfully, including packaging and clean Ubuntu installation checks.

**The failure did not reproduce and its root cause remains unknown.** The earlier
failure is retained; a green rerun is not proof of a production bug fix. That rerun
does not contain the diagnostics added here. See the
[activation investigation](../ci-activation-followup-2026-09-27.md).

## Validation and compatibility

- Versioned full-feature Rust suite: **904 passed, 0 failed, 27 ignored**. Strict
  all-feature/all-target Clippy and Rust formatting pass. Opt-in desktop environments
  remain separate; ordinary suite success does not qualify every application or model.
- All **5** diagnostic-wrapper tests and **14** editor-observer tests pass. ShellCheck,
  Python syntax, workflow wiring, unchanged dependency versions and platform metadata
  checks pass. Changed-document local links and both functional-network diagrams agree.
- Default and inline-preedit private IBus suites pass in the resource-limited resumption,
  followed by **10** activation/release cycles. Both complete native suites retain the
  previously failing bilingual and long-adopted sentence workflows, with no deadline
  or assertion changes. The initial failures remain documented below.
- All four Linux release binaries build; the CLI reports **0.7.1**. Local `.tar.gz`
  and `.deb` package-content, checksums, launchers, offline audit links and non-installing
  smoke checks pass. These worktree QA packages are not published release assets and
  do not establish clean-container installation acceptance for the new version.

The first default IBus run during this release check passed activation/restoration,
then received an empty language-change response in `check_bilingual_core_completion`,
raising `JSONDecodeError`. Other build/test work was running concurrently. A separate
default run also passed activation and the bilingual cases, but failed with the same
empty response in `check_long_adopted_sentence_continuity`. The second result rules out
treating the failure as merely a concurrent-build incident.

A third, syscall-traced diagnostic run reached the existing 120-second suite limit
(exit 124), not a pass. Its host file-sync calls reached approximately 0.77 seconds;
the IPC server has a one-second deadline, but the trace did not establish the cause
of the earlier empty replies. No timeout or assertion was relaxed, and no production
fix was applied. The inline and activation-repeat checks queued after the failing
default suite did not run in this release pass. These results are separate from the
earlier 0.7.0 activation/restoration failure; the initial attempts were not all-green.

After the user reported an OOM, the kernel log confirmed a global OOM at **14:24:59
Asia/Shanghai on 2026-09-27**, terminating a VS Code process. This was later than the
failed checks above, so it does not establish their cause. No test processes remained;
the resumed session had approximately 7.8 GiB available and no current memory-pressure
stall. The unchanged default and inline-preedit native suites then both passed when
run sequentially with one Cargo build job, `MemoryHigh=2G`, `MemoryMax=4G` and
`MemorySwapMax=0` in dedicated user systemd scopes. The earlier failures are retained:
successful reruns are not a production bug fix or proof of an OOM-related cause.
The follow-up 10-cycle activation/release check also passed under the same limits,
and the kernel log showed no new OOM during this resumption. No unrelated applications
were stopped, and the installed input service and personal settings were not changed.

Rust/lockfile, macOS bundles and Android metadata use **0.7.1**. Bundle build numbers
and the Android version code are **25**. Dependency versions are unchanged. This source
release does not replace the currently installed 0.7.0 programs or attach binary assets
to a GitHub Release. Local checks, remote CI and installation acceptance are separate.

## Install and upgrade

Once matching assets are available, verify `suzaku_0.7.1_amd64.deb` with
`sha256sum -c suzaku_0.7.1_amd64.deb.sha256`, finish/cancel the draft, fully quit Suzaku,
then use `sudo apt install ./suzaku_0.7.1_amd64.deb`. Upgrade the panel and host together.
Existing settings, shortcuts and cloud-consent rules are retained. Source/user installations
must likewise replace matching binaries. Hosts registered before 0.6.5 still require explicit
re-registration for the service retry policy; see [Linux installation/data](../linux-packaging-data.md).
