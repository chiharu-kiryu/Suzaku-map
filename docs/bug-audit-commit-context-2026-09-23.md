## N32：宿主沿用编辑器的自动分隔，模型上下文多出空格

优先级 P2。[通用引擎](../src/ime/core_engine.rs) 的独立编辑器提交按语言自动拼接，
英语两次提交之间默认插入一个空格。这个规则适用于编辑器内部累积文本，但
[原生宿主](../src/ime_host.rs) 只向应用交付候选本身，没有交付该额外分隔符。

宿主先前复用了编辑器的提交方法，导致实际交付载荷与内部累积上下文不一致：
`foo`、`bar` 两次提交交付 `foobar`，模型请求却带 `foo bar`；`hello `、`world`
交付 `hello world`，模型看到 `hello  world`。额外空格也影响最近 160 字符的截取。

这是模型输入上下文错误，不是应用正文被插入了额外字符；本轮不修改已交付文本。
此处上下文仅指本字段经宿主候选提交的历史，不是应用当前文档或周边文本的实时镜像。

## 修复前证据

先在 [私有 IBus 套件](../scripts/test-native-sync.py) 中连续提交固定候选，记录真实
CommitText 事件，再启用测试拥有的回环模型服务，比对请求的 `committed_context`。
覆盖 Enter 和伴随面板候选提交两种路径，**20 组中 12 组失败、8 组对照通过**：

```text
AUDIT: N32 en/identifier/enter: expected='foobar', model='foo bar'
AUDIT: N32 en/trailing-space/panel-click: expected='hello world', model='hello  world'
AUDIT: N32 en/leading-spaces/enter: expected='hello  world  ', model='hello   world  '
AUDIT: N32 en/unicode/panel-click: expected='café\u3000日本😀', model='café \u3000 日本😀'
```

六类英文场景的两种提交路径均失败；中日文原有提交分隔为空，八组转换/原文对照通过。
测试同时断言每个应用提交载荷未被改变，模型请求本身不触发额外提交。

## 修复及边界

- 通用引擎增加仅供 crate 内宿主调用的原样提交入口；成功提交时直接追加完整候选，
  不插入独立编辑器的分隔符。宿主切换到该入口。
- 两种入口共用候选校验、确认门槛、内部历史记录、预测取消及草稿清理流程，
  不绕过拒绝提交的条件；失败或空提交不更改上下文。
- 独立面板和公开引擎 `commit` 仍采用原有语言分隔规则，内部撤销也保持原行为。
  宿主内部历史检查不代表可以撤销应用已经接收的正文。
- 模型请求仍只携带本字段最近 **160 个 Unicode 码点**；不改请求格式、提供器、
  授权、隐私或焦点隔离。私有字段仍不保留提交上下文，提供器身份变化仍清理旧上下文。
- 共用宿主代码也用于其他原生适配器，但本轮真实宿主验收仅覆盖 Linux / IBus，
  不宣称完成 macOS、Windows 或 Android 的端到端验收。
