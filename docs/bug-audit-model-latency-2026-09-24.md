基线仍为 `0.6.5` / `088c5d94e49b701e9c11074c650ea558a9a59a55`，以下为未发布源码改进，

## 结果摘要

- 默认候选请求从最多 6 个带类型的对象精简为 2 条完整字符串；旧响应格式仍兼容。
- 本机 CPU `llama3.2:3b` 在最终一次 **5 秒私有测试预算**下，三语探针 **7/7** 返回有效
  候选，约 **763–1700 ms**。此前同机旧请求为 7/7 超时。
- **默认 1200 ms 仍不稳定**：最后一次英文探针 3/5 成功，另 2 项超时；不能宣称全部解决。
- 真实 Chrome → IBus → 模型候选采用/撤回/续写/精确单次提交通过，加上原有保护共 **7 组**。
- 翻译强化任务指令，并拒绝丢失原文问号的结果；仍有日文错译/遗漏与韩文混合语言问题。

没有换模型、按模型名分支、放宽前台等待、自动重试、默认预热或云端回退；没有下载权重、
重启个人 IBus/Ollama、改变个人配置或安装。只在私有配置、Xvfb 与 D-Bus 会话中使用合成文本。
Ollama 为 0.33.3；模型仍为已有的 3.2B Q4_K_M、CPU 推理。空闲驻留请求仍为 5 分钟，
不调用卸载或接管服务进程。

## 1. 候选时延：减少模型必须生成的内容

旧请求不仅携带重复的词头/前文、默认置信度和空提示，还要求最多 3 个词、3 个句子，
每个条目重复 `text` / `kind`。一次放宽到 30 秒的**诊断**拿到了完整服务端计数：

| 单次诊断样例 | 提示 tokens / 处理耗时 | 输出 tokens / 生成耗时 | 总耗时 |
| --- | --- | --- | --- |
| 旧请求 `hel` | 366 / 2765 ms | 122 / 6238 ms | 9007 ms |
| 新提示第一次 `hello` | 140 / 955 ms | 11 / 533 ms | 1502 ms |
| 随后 `hel` | 140 / 186 ms | 11 / 544 ms | 735 ms |

三者报告的模型载入耗时均为 0；重复提示可复用服务端计算，新提示首轮仍更慢。这里是定位
开销的单次观测，不是统计性能基准，也不能把诊断的 30 秒期限当成生产期限。期间试过复杂
前缀 schema，实际出现无效输出，**未保留该方案**；最终只用简单 JSON 字符串约束，精确
前缀、完整响应、去重、控制字符与长度上限继续在程序内校验，不修补截断或漏掉的前文。

最终 [请求实现](../src/languages/model.rs)：

- 请求两条完整替换文本，一个词补全和一个短续写；不再让模型生成类型标签。
- 保留语言、原文、本地转换、提交上下文和英文补全模式；只在有实际信息时带置信度/降级/手写提示。
- 保留现有模型接口、授权、温度、输出上限与 20–5000 ms 候选预算，默认仍 1200 ms。
- 旧的最多 6 项类型对象、3 项字符串数组和 compatible 纯文本仍可解析；词句分类、派生与混排仍在语言层。

又捕获到一类真实坏输出：外层 JSON 合法，但候选字符串里夹着
`'local_conversion':'hel','raw_composition':'hel'` 等请求数据。新增过滤只检查**生成部分**，
出现至少两个不同的带引号/冒号的请求字段键即丢弃；不修改已输入内容，也不删除普通字段名
提及。Ollama/compatible 的回归均确认坏项消失、同响应中正常 `helmet` 留下。
这是一类协议回显保护，不是任意乱码或语义错误的通用检测器。

### 生产期限下的复测

构建完成后顺序运行、无同时模型推理或构建；单独配置的候选温度保留默认 0.4。
最终 `model probe all` 的 5000 ms 结果为：

| 原文 | 耗时 | 通过解析的模型结果 |
| --- | --- | --- |
| `nihao` | 1700 ms | `你好，` / `你好吗？` |
| `hello` | 1333 ms | `hello world` / `hello again` |
| `hel` | 790 ms | `helmet` / `helix` |
| `please sen` | 1031 ms | `please send` / `please send you` |
| `good m` | 763 ms | `good morning` / `good man` |
| `thank you ` | 921 ms | `thank you very` / `thank you so` |
| `nihongo` | 941 ms | `日本語の意味` / `日本語の使い方` |

随后将私有配置恢复 1200 ms，`model probe en` 的 `hello` / `hel` / `good m` 分别约
724 / 780 / 759 ms；`please sen` / `thank you ` 分别在 1215 / 1224 ms 超时，命令正确
以失败退出。更早同提示的 5000 ms 试跑也曾在 `thank you ` 超时；结果具有波动，不能只挑
最终成功的一次宣称稳定。以上“有效”指通过协议/前缀等检查，**不是语言质量评分**。

## 2. 真实输入的正向链路

[实模运行器](../scripts/test-linux-model-live.py) 保留原来的六组 1200 ms 安全测试，新增
`SUZAKU_MODEL_QA_REQUIRE_CANDIDATE=1`，明确启用第七组 5000 ms 正向验收：

```bash
SUZAKU_MODEL_LOCAL_QA=1 SUZAKU_MODEL_QA_MODEL=llama3.2:3b \
  SUZAKU_MODEL_QA_REQUIRE_CANDIDATE=1 bash scripts/test-linux-apps.sh model
```

连续两次完整运行均为 7 组通过。默认预算的 `hel` 在前次为 Ready，末次仍为 Unavailable，
这也体现了短预算的波动；不能把允许回退的安全组当成生成成功。两次额外正向组的
`Could you sh` 得到来源为 **model** 的 `Could you show`（不是被模型确认的离线候选）。
实体数字键采用后正文为空、退格撤回到原稿、再次选择真实模型项后续写 ` today`，Enter
只提交一次完整可见草稿；提交后旧响应没有回填。

断言同时检查实际网页正文、宿主草稿/候选与 IBus 提交信号，透明转发器不合成模型回复。
第一轮扩展夹具因大写字符不属于原有小写输入帮助函数而停下，改为真实 Shift+C 后才执行
完整正向测试，不算产品缺陷。撤回后允许下一次模型采样变化，验收的是当前可见候选，不
要求模型重复生成相同句子。`Unavailable` 或只有离线来源不能通过该正向检查。

## 3. 翻译：任务更明确，失败不伪装成功

[翻译提供器](../src/languages/model/translation.rs) 在未改动的源文本前重申翻译任务，
提示保留问句、否定、数字、名字与段落；温度为 0，不注入已提交上下文或手写提示。
短文本使用 512-token 输出上限和与候选相同的 2048-token Ollama 上下文，避免一次短翻译
切到 8192 后又切回；较长输入保留 4096/8192 的预算，总期限仍是 30 秒。
具体短请求字节条件见 [翻译说明](translation.md)。

[翻译接口](../src/languages/translation.rs) 与工作线程检查原文 `?` / `？` 数量是否减少。
不合格时显示八语错误提示、保留原稿，不在回答末尾补问号，不自动重试；面板不能应用失败
结果。这是保守的标点契约，省略问号的正常译法也可能被拒绝；保留问号仍可能翻错。

最终实模观测：

- 八目标问候冒烟通过文本/脚本/问号检查，英文同语种直接返回，不发请求。中文为
  `你好，你好吗？谢谢你帮忙。`，不再把问题改成回答。
- 日文问候仍遗漏“你的帮助”；韩文仍含 `how are you?`。冒烟通过不能算语义合格。
- 独立报告样例 `Can you send the report by Friday? Do not change the numbers.` 中文
  保留问句与否定；日文被 `LostQuestionForm` 拒绝，原文保留。
- 另一独立样例 `Please keep order 42. Can we meet at 3 pm?` 的日文虽保留问号，却错误
  改写前句，仍通过有限检查。这直接说明保护不能替代语义验收，也不能宣称小模型已经胜任。

只隔离和减少可检测的坏输出，不强制更换或下载模型。接口与具体模型身份仍解耦。
